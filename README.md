# Dovetail

Dovetail (called Payday up to version 2.8) is an Android app for the monthly household transfers: type in take-home pay, and it works out the transfers to make between your accounts, in order, so every bill, budget and savings transfer is covered and you can see what's left over for the month (the "float" in the code and data). It also tracks renewals, reminders and known one-off payments, and an Analysis tab shows the months ahead and where the money goes (month by month, savings rate, bills by category, pay history and savings so far). A guided tour and plain explanations help someone new to budgeting. Optional reminder notifications, appearance settings, backup files that open on another phone, and exports for a spreadsheet or an AI assistant. Offline (no INTERNET permission). Package `uk.whiteboard.payday`.

Everything is worked out from what's entered in the app: people, accounts, where each account's leftover goes, bills, other income, spending budgets, savings transfers and one-offs. Nothing about any household is built in; a new install starts with a seven-step setup (see "Setup, the checklist and Start again" below).

## Building
Requirements: JDK 21+ (the Robolectric tests need it for Android 36; the app compiles for Java 17), Node 18+, Android SDK with platform 36 and build-tools 36.0.0.
```
export ANDROID_HOME=/path/to/android-sdk
export PAYDAY_KEYSTORE=/path/to/payday-release.jks
export PAYDAY_KEYSTORE_PASS=...
./build.sh
```
Output: `app/build/outputs/apk/release/app-release.apk`, and the app bundle for Google Play, `app/build/outputs/bundle/release/app-release.aab`, signed with the same key (`build.sh` checks the two certificates match and that neither has INTERNET). Updates only install over the top if signed with the same key (alias `payday`).

Maven Central sometimes rate-limits shared build machines (HTTP 429). `settings.gradle.kts` lists Google's official Maven Central mirror first, and Robolectric is pointed at the same mirror.

For each release: bump `versionCode`/`versionName` in `app/build.gradle.kts` and `VERSION` in `web/src/ui.js`, and add a CHANGELOG entry (and the "What's new" lines in `ui.js`).

## How the transfers are worked out
Words on screen (2.6) are plain words for someone new to budgeting: the float is "left over", a budget month is a "pay month", projected figures are "estimated". The code, data fields and the exports keep the older names (float, leftover, budget month).

For each account: money in = pay of the people paid into it (typed in, or estimated from the last month that has it, or their usual pay) + other income + one-off income; money out = bills due that month + spending budgets + savings transfers + one-off payments.

Each account has "Leftover goes to" another account (on screen: "What's left moves to"), or keeps its leftover ("Keeps what's left"). Working up from the accounts nothing sends to: an account's subtotal is its own in − out plus what its children pass up. A positive subtotal is sent to the parent; a negative one is a top-up from the parent; an account that keeps its leftover holds its subtotal as the float. Steps are listed surplus transfers deepest first, then top-ups from the top down, then savings transfers. Settings won't let you create a loop. A reconciliation check confirms total floats = total in − total out. It's silent when the figures add up; if they don't (for example a bill pointing at an account that no longer exists), the Pay tab's hero shows a warning with how far out it is and an "Open accounts" button (`#check`).

Step ids (used for ticks): `t:<from>><to>` and `s:<savingsId>`.

## Data
- The page stores everything in WebView localStorage for the origin of `file:///android_asset/index.html`. **Don't change that URL** (for example to WebViewAssetLoader's https://appassets.androidplatform.net) without a migration: a different origin starts with empty storage.
  - `payday.config.v1` (schema 5): `people` {id, name, payAccount, usualPay}, `accounts` {id, name, colour, leftoverTo}, `bills` {id, name, amount, account, months, renews?, lead?, note?, savings?, savingsSince?, category?, categoryAuto?, history?: [{on, date, from, to}]}, `income`, `budgets`, `savings` {id, name, amount, fromAccount, since?} (`since`: the budget month it started, from which Saved so far counts it; set to the month it is when added in Settings, and by setup as described below), `reminders`, `payday`, `doneLog`, `setupDone`, `example` (example household only), and from 2.2 (optional, defaults in `normCfg`, still schema 5): `appearance` {theme: system/light/dark, textSize: small/normal/large}, `notify` {on, time "HH:MM", amounts}, `lastVersion` (for "What's new"), and from 2.6 (optional, still schema 5) `setupTips` (true after a new setup: the Pay tab's "Finish setting up" card; missing means off) and `tourDone` (false until the guided tour has been shown; missing means seen). `normCfg` keeps these two only when they say something (`setupTips: true`, `tourDone: false`), so an existing household's saved settings never change.
  - Bill categories: housing, utilities, insurance, transport, children, health, subscriptions, memberships, debt, savings, other. A suggestion from the name (generic words only) has `categoryAuto: true` and follows renames; a category the user picks (including "Not categorised", stored as `""`) is never overridden. The Savings category and the savings tick are kept in step.
  - `payday.months.v1`: per budget month: `pay` {personId: amount or null}, `payEstimated`? {personId: true} (2.7, optional: that person's saved pay is the estimate filled in when a transfer was ticked before pay was typed; it goes when the box is typed in, and a month without it reads exactly as before), `done` {stepId: amount when ticked}, `oneOffs` [{id, kind "out"/"in", name, amount, account, date?}], `results`. Backups copy months as they are, so `payEstimated` travels with them; still backup version 5.
  - `payday.wealth.v1`: the old Wealth tab's data. 2.0 doesn't use it, never changes it, and keeps it in every backup.
  - `migrate(c, m, w)` runs on load and on restore; each step is idempotent. 1.x data (schema 3 and older, recognised by `looksLegacy`) is turned into editable people and accounts in the old built-in shape, keeping the account ids so bills need no change. No names are built in (2.8): the accounts get plain names ("Current account 1", "Current account 2", "Joint bills account", "Joint spending account") and the people, their ids and names come from the 1.x data (`legacyPeople`: defaultPay's keys, then the months' pay fields; `nameFromKey`); ticks are renamed, the overdraft becomes a one-off, and mortgage deal ends move onto the mortgage bills. Schema 4 → 5 suggests bill categories.
  - `normCfg` and `normMonths` (2.8) check settings and months item by item whenever they're opened or restored: a payday day that isn't 1–31 or "last" counts as not set, bill months are whole numbers 1–12, items and months that aren't objects are dropped, and ticks, pay and one-offs of the wrong shape are fixed. Sound data goes through unchanged.
  - `payday.errors.v1` (2.8): the last ten unexpected errors (time, version, message, where in the code; never names or amounts), listed in "Copy app details". `payday.broken.v1` (2.8): one copy of data the recovery screen set aside; Settings › Backup can copy it out or remove it.
- If the saved data can't be read, or opening it throws, the page shows a recovery screen ("Dovetail couldn't open"; "Payday couldn't open" in 2.8) instead of the app: restore one of the automatic backups, open a backup file, start again (two taps) or copy the app details. Nothing is changed until one is chosen, and the data that was there is set aside first (if it can't be, nothing happens). Unreadable data is never treated as a new install.
- Backups (Copy backup, Share, automatic): `{"app":"payday-transfers","version":5,...}`. A restore is tried on copies first (including working out the month to open on) and refused before anything is saved if it can't be opened; pasted text over 2 MB, or from another app, is refused. Backups from any earlier version restore through the same migration; newer versions are refused. Restoring never replaces Wealth data already on the phone.
- Saving: pay and one-offs save 0.7 s after the last change, settings 0.6 s; anything pending is saved at once when the app goes to the background.
- Automatic backups: `files/backups/backup-YYYYMMDD-HHMMSS.json`. Written 2.5 s after the last change (or when the app goes to the background), skipped when nothing changed, never for the example household or before setup. Kept: 10 newest + newest per day for 14 days, plus backups made just before a restore (`backup-…-keep.json`) for 30 days (at most 5).
- Android settings (SharedPreferences `payday`): `app_lock`, `theme` (the Appearance theme, applied to the window before the page loads), `notify_on`, `notify_schedule` (the page's latest schedule), `notify_posted` ("date|key" of notifications already shown, kept 100 days).
- Android backup (`allowBackup=true`): only `files/backups/` is included, only when end-to-end encrypted (`backup_rules.xml` for Android 10–11, `data_extraction_rules.xml` for 12+). On a fresh install that finds backups, setup offers to restore the newest.

## Analysis tab
Derived only: nothing new is ever asked for, and the tab can't see actual spending, so it judges the plan (the float, called "left over" on screen), never spending against it. Cards, in order, most with a one-line verdict first and a "Show as table" view:
- **Month by month** (first, because "am I OK?" is the question): the float for 12 budget months, 3 before the one on screen, that month (labelled "this month") and 8 after. The verdict names this month's float (a red banner when it's short, with any other short months), then the tightest month ahead and the heaviest month (most going out) with what makes it so. One chart (the float); the outgoings are in the readings and the table's Bills, Budgets, Savings, One-offs and Going out columns, with `monthExtras` ("What's different": bills not paid every month that are due then, and one-offs) and a one-offs line under the chart. A month with typed pay (`payIsTyped`: not a figure marked in `payEstimated`) is "actual" and drawn solid, with a short ink line at its predicted float: what the app showed before pay was typed (each person's pay from the latest earlier typed month, or usual pay; no line when there was nothing to predict from). Other months are projected ("Estimated" on screen) and drawn hatched (an SVG pattern). The month on screen (2.7) has a 2px ink outline on its bar and a bold ink label that's always shown (when labels are thinned to every other month, its neighbours drop instead), and "(this month)" in its reading and the chart's description; Pay and what was left marks it the same way when it's in that chart. Estimated pay (`payEstimated`) isn't typed pay: it's left out of averages, history and the predicted line, and the month stays hatched.
- **The monthly picture**: the savings rate ("Saved from pay"), then income split into bills, spending budgets, savings and average left over. "The average month" spreads bills that aren't monthly over 12 months and uses each person's average typed pay over their last 6 typed months (or usual pay). Savings rate = (savings transfers + bills marked as savings) ÷ income.
- **Where the money goes**: bills by category, subscriptions and memberships as a highlighted line at the top. Bills marked as savings are bills here but saving in the monthly picture; the Savings row says so, as the two "bills a month" figures differ by exactly those. Hidden, like Month by month, until there are bills, budgets or savings.
- **Pay and what was left** (pay and float history, once two months have typed pay), **Saved so far** (ticked transfers and bills marked as savings; how consistently each was ticked is in its table), **Price changes** (renewals recorded in 2.1 or later; hidden until there is one) and **Accounts that ran short** (top-ups, with a line saying what a top-up is; hidden when there were none). History, saved so far and top-ups use months where pay was typed or a transfer ticked.
Charts are inline SVG (no libraries); keyboard readings go to a live region. Chart colours are a validated categorical palette (`--viz-1`…`--viz-8`, separate light and dark steps).

## Appearance
Settings › Appearance: theme (follow phone, light, dark) and text size (smaller, normal, larger). The theme sets `data-theme` on `<html>`; text size sets `data-text`, a root font-size multiplier of 0.9 / 1 / 1.15 (every CSS font size is in rem; chart text scales too). The page tells the app the theme (`setTheme`), and the app stores it and applies it to the window background, the lock screen and the status and navigation bar icons on every start. Android's own night mode isn't switched (that would restart the screen), so the launch splash still follows the phone.

## The Pay tab (2.7)
From the top: the month bar; at most one notice (`#notice`, `renderNotice`), the first of a restore offer, What's new, or the example banner / "Finish setting up"; the hero; the reminders nudge (`#actionBanner`), one line that ends in "…" when it's long; take-home pay; the transfers, with "N of M done" and **Share** (`#shareTransfers`) in a row that wraps, and under them, when bills that aren't monthly are due, "Includes 1 bill that isn't monthly: £168.00 — see This month in detail." (`#nmNote`, which opens it at Not every month); **This month in detail** (`#payDetails`, with the left over beside it): Not every month, the one-offs, each account's figures and the month's totals, laid flat on the sunk tone; Bills by account; **Saved months** (newest first, "Ahead" then "This month and earlier"; "Pay not typed in" when nobody's pay was typed, "(estimated)" by a figure from `payEstimated`).

This month in detail is closed, except that it opens by itself in a month with one-offs (something typed for that month, which changes its transfers), until it's opened or closed by hand; that choice is kept for the session only (`payDetailsOpen`, not saved). A one-off's link, Reminders' "Open <month>" and the line under the transfers open it first and count as opening it by hand (so it then stays open for the session); the tour's one-offs and Not every month stops open it too, and the tour puts it back as it was.

**Share** builds plain text with `transfersText(c, k, r, done, payInfo)` in `export.js`: a title with the pay month and payday, one line per transfer in order with ☑ or ☐, "(top-up)" where it applies, "(ticked at £2,132.00: £50.00 more to send)" when the amount has changed since it was ticked, what's left over (one line per account that keeps what's left when there's more than one), and "Amounts use estimated pay for Alex and Sam." when pay is estimated. In the app it goes to the share sheet as text (`shareText`); in a browser, to the browser's own sharing if there is one, otherwise it's copied.

**Ticking before pay is typed** fills the empty pay boxes with the estimate (the ticks are for those amounts) and marks them in `payEstimated`; the hint under the box says "Using Oct 2026: £2,150.00 (estimated — tap to type what arrived)" until a figure is typed.

**Remind me** for a bill's first renewal date (2.7, `defaultLead`): a week before for a monthly subscription or membership, otherwise a month. Only when a renewal date is first set in Settings › Bills and no choice was made; a stored choice never changes.

## Look and feel (2.3)
Design tokens in `web/template.html`: `--bg`, `--surface`, `--sunk`, `--hair` (most separators), `--line` (input borders, table rules), `--ctl` (the tick's outline, 3:1), `--ring`, `--shadow` (light mode only), `--r` (cards, 20px) and `--r-in` (14px), each with light and dark values. Section titles are sentence case. `moneyEl()` sets amounts with smaller pence (textContent unchanged). `avatar()` draws an account badge whose initials come from CSS (`data-i` and `::before`), so they never add to text read by screen readers or tests. The Pay tab hero (`renderHero`, "Left over this month") shows the total float, a progress ring and, only when the figures don't reconcile, a warning (`#check`). `animatePanel()` fades a page in on a tab change, or slides it when the month changes (swipe or arrows); `rollHero()` rolls the float; every animation is skipped under reduced motion. Ticking calls `haptic("tick" | "untick" | "done")` on the bridge, which uses Android's performHapticFeedback (no permission).

## Setup, the checklist and Start again (2.6)
- **Setup** (`#tab-setup`, with no tab bar or month bar) runs on a new install, after "Set up my own household" in the example household (a green button that turns red only after the first tap: "Tap again: this clears the example"), and after Start again. Seven steps, each saying "Step N of 7", with focus on its title:
  1. Welcome: "Set up my household", "Restore from a backup" (open a backup file or paste one; on a phone with automatic backups, the newest is offered first) or "Explore an example".
  2. Your pay: each person's name and usual take-home pay (explained in plain words), with other regular income behind a link.
  3. Your payday: whether everyone's paid on the same day (if not, the day the transfers are made), the day or the last working day, and whether a weekend payday moves to the Friday before. It shows the next payday and the pay month it's for.
  4. Your accounts: four starting points, worded for one person or more, each with a small diagram (one account; a bills account then a spending account; own accounts then a joint one; separate accounts for bills and spending), built by `setupShape` in `calc.js`. Then the accounts to check, where each pay arrives, and a diagram of how money moves (`flowDiagram`, also in Settings › Accounts and How Dovetail works; accounts sit side by side, two to a row at most, from 400px wide with normal text) with a worked example. Each account from a starting point has a role (Alex's own account, joint, bills, spending…): when the starting point is filled in again, after someone is added in step 2 say, accounts with the same role keep their ids, so what was typed for them stays put.
  5. Your bills, account by account: every month, once a year or some months (`billMonths`), with suggestions that hide once a bill with that name is there. The usual bills account opens with three rows: one nobody is paid into that passes what's left on; with none, the account everyone is paid into if it passes what's left on (`sharedPayAccount`: one person's "bills account, then a spending account"); otherwise the account that keeps what's left. Settings › Bills › Quick add starts on the same account (`defaultBillAccount`, both in `calc.js`).
  6. Spending budgets and savings transfers, kept in and sent from the account that keeps what's left unless changed.
  7. Your first payday: the next payday from today and the pay month it's for (`nextPayday`), then the transfers in order and what's left over, worked out with the real calculation from usual pay (with no pay at all, the transfers without amounts).

  Back keeps everything typed. "Skip this step" (payday, bills, spending and saving) leaves that step out until Next is pressed on it again. Nothing is saved until setup finishes.
- **Finishing** (`setupResult`, `finishSetup`): "Looks right, start" on step 7, or "Finish later" on steps 2–6 ("Skip setup for now" on step 1), keeps what was entered and fills in the rest: with nobody entered, one person "You"; with no accounts, one "Current account" that keeps what's left; anything not reached is left empty, and rows that aren't complete (a name with no amount, a yearly bill with no month) are left out, with a message once the tour has ended ("2 rows weren't complete, so they were left out. You can add them in Settings."). It saves `setupDone`, `setupTips: true`, `tourDone: false` and `lastVersion`, keeps the appearance and notification settings, backs up straight away and starts the tour. After "Looks right, start" the Pay tab opens once on the month the preview showed, and savings transfers start (`since`) in that month. After Finish later, and whenever the app opens later, it opens on its usual month (`defaultMonth`), which is also the month Finish later's savings transfers start.
- **"Finish setting up"** (`#setupTips`, at the top of the Pay tab while `setupTips` is true): a checklist from `setupChecklist(cfg, months)` in `calc.js`: take-home pay (every person has usual pay or typed pay), payday, bills, and spending budgets or savings, with "N of 4 done". Each item not done is a button to its Settings section; done ones are ticked. When everything's done, or "Hide this" is tapped, `setupTips` is removed and the card doesn't come back. Never for the example household or an existing household (neither has `setupTips`); a restore brings back whatever the backup had, so only a backup made while the card was showing brings it back.
- **Start again** (the end of Settings › Backup, export & restore; on the phone only, as it needs somewhere to keep a backup; never for the example household), with a second tap to confirm: anything waiting is saved, then the figures are kept as a backup on the phone (`keepBackup`, kept 30 days); if that fails, nothing changes. The phone's reminder schedule is cleared, the months are removed and the settings are cut down to this phone's own, `{schema, appearance, notify}` with no `setupDone` (never touching `payday.wealth.v1`), and setup starts, offering to bring the backup back ("Restore backup" or "Start fresh"); setup's history entry replaces Settings', so Back on Pay later leaves the app at once. App lock, notifications on or off, the notification time and the appearance stay as they were, even if the app is closed before setup finishes: any settings without `setupDone` open setup, with their appearance, offering the newest automatic backup.

## Help, the tour and hints (2.6)
- **"What's this?" buttons**: a small round "?" (a 44px tap area, named as a question such as "What does left over mean?") next to the headings a newcomer may not know: left over (the hero), take-home pay, the transfers, not every month and one-offs on the Pay tab; month by month, the monthly picture, where the money goes, saved so far and price changes on Analysis; Reminders. Each opens a bottom sheet with a short, plain explanation from the `HELP` map in `ui.js`, using the household's own figures where that helps ("November 2026: £415.90 left over in Joint spending", "Of every £100 that comes in, £12 goes to savings").
- **The sheet** is a modal dialog (`#sheet`): focus starts on its title and stays inside it; Esc, Close, a tap outside it and the phone's Back button close it (it adds one history entry, which closing removes), and focus goes back to the "?" that opened it. Everything behind is `inert`.
- **Settings › Help** (`#sHelp`, after Backup, export & restore and above About; Settings in 2.7: People, Accounts, Bills, Other income, Spending budgets, Savings transfers, Payday, Appearance, Reminders & notifications, App lock, Backup, Help, About): "Show me around" (`#tourStart`), "How Dovetail works" (the routine, how money moves with the household's own diagram, what left over means, pay months) and "Words Dovetail uses" (a glossary of eleven words).
- **The guided tour**: shown once straight after setup finishes (including Finish later and Skip setup for now: `tourDone` false), and any time from Settings › Help or the example household's banner. Never for an existing household, after an update or after a restore. Stops, in `TOUR`: the month bar, the hero (with the real left-over figure, or what's short), take-home pay, the transfers, one-offs, Not every month (only when there are bills like that), then the Analysis, Reminders and Settings tabs (the tour switches tab for these three). Stops whose element isn't on screen are left out, and "N of M" counts only those shown. Each stop rings its element (3px accent ring, the rest dimmed) and scrolls it clear of a card docked above the tab bar (an element taller than the space shows its top part). The card is a modal dialog labelled by its title and described by its text; focus goes to the title at each stop and stays in the card; the ringed element is described by the card's text while ringed. Esc, Skip tour and the phone's Back end it; Done ends it on the last stop, which also gives the routine. Swipes and taps behind it do nothing. While it runs the tour has one history entry of its own, which moves with it from tab to tab (`goTab` replaces it), so the phone's Back ends it on any tab, the Pay tab included, and lands on Pay; ending it any other way removes the entry (`tourUnwind`) and returns to where it was started. Ending it any way removes `tourDone` and saves. No transitions under reduced motion.
- **First-month hint**: "First payday? Open your banking app, make each payment below, then tick it here." above the transfers, until some month has every transfer ticked, or a month other than the one on screen has a tick or typed pay (`firstMonthDone(months, k)`, worked out from the saved months; nothing new is stored), so a household that has used Dovetail before never sees it. Never for the example household, or when there are no transfers.

## Swipe between months
A sideways swipe on the main area moves one budget month, exactly like the ‹ › arrows (`stepMonth`, which calls `goMonth` and slides the page in): left for the next month, right for the previous one. It works wherever the month bar shows (Pay, Analysis, Reminders) and does nothing on Settings or during setup; tabs change only by the tab bar and Back. It must be at least 70 px sideways with less than half that vertically, must start more than 24 px from either screen edge (Android's back gesture), and is ignored when it starts on a chart, a sideways-scrolling table, a form field, or anything marked `data-noswipe`. Passive touch listeners, so scrolling is never delayed. A short slide only when reduced motion isn't requested. Changing month saves anything typed first; a one-off being edited closes (saved to its own month), and a new one-off still being typed stays open for the month now on screen. On Reminders an open editor or renewal form stays open with what's typed (a renewal's typed date and amount are kept until it's saved or cancelled): it shows in the section it was opened from while the item is listed there, otherwise in Needs attention, the month or All upcoming (opened for it); a delete waiting for its second tap is cancelled.

## Reminders by month
The Reminders tab has the month bar too, and the month on screen is the same one as on Pay and Analysis. From the top:
- **Needs attention**: overdue and due-soon items counted from today, whatever month is on screen. It drives the tab's badge and the Pay tab's banner, and never moves with the month.
- **In <month>**: the bill renewals, your own reminders and dated one-offs whose date falls in that budget month's window: from the payday that funds it (inclusive) to the day before the payday that funds the next month, or the calendar month when no payday is set. Money for a budget month arrives on its payday, so what falls between that payday and the next is what that month's money has to cover. Dated one-offs are placed by their date, whichever month they're saved under, and ones whose date has passed still show in their month, marked "One-off, passed" (they've happened, so they're not overdue). Each row still counts its days from today, so an item can be in both lists: then (2.7) the month shows it as one line with no buttons, "Gym · 9 Nov 2026 · in 20 days — listed above", keeping its `rem_m_` id. The heading has a hint, "‹ › change month above", until the month is changed on Reminders once (for the session). `monthWindow(pc, k)` and `remindersInMonth(c, months, k, today)` in `analysis.js`.
- **All upcoming** (collapsed; stays open for the session once opened): everything ahead, grouped by calendar month.
- **Recently done** and **Add your own**. A new reminder starts on the window's first day when the month on screen is still ahead, otherwise 30 days from today.

Notifications and the badge are about today and don't change with the month. Opening Reminders from the Pay tab's banner or a notification keeps the month on screen. A one-off's "Open <month>" button goes to the Pay tab at that one-off's month. The Reminders page title is an h2 there, so the month bar's h1 is the page's only h1, as on Pay and Analysis.

## Opening and importing backup files
Dovetail opens its backup files, including those made when it was called Payday. `OpenFileActivity` (no screen of its own) takes `ACTION_VIEW` for `application/json` and `text/plain` (a file tapped in WhatsApp, Files or email; some apps label .json files as text) and `ACTION_SEND` for `application/json` (a file shared to Dovetail; not `text/plain`, which would put Dovetail in every share menu for any text or link). It reads the file from the content link while it holds access (no storage permission), refuses it over 2 MB or if it isn't a Dovetail backup, and hands the result to MainActivity through a private file (its own name each time, written before it appears, read once), with NEW_TASK | CLEAR_TOP | SINGLE_TOP so the open Dovetail receives it. Only `content://` links are read. MainActivity keeps its normal launch mode, so tapping the app icon never closes a file picker, permission prompt or share screen. The hand-over and notification intents are MAIN/LAUNCHER like the icon's, so a Dovetail started from a file or a notification is the same task the icon brings back; and if the icon ever starts MainActivity on top of an existing one, it closes itself straight away. Reopening from Recents (FLAG_ACTIVITY_LAUNCHED_FROM_HISTORY) is ignored. As a last line of defence the page itself never saves over newer data: it remembers the settings and months it last read or wrote, and if storage has changed underneath it (another copy of the page), it takes the newer data instead (on the `storage` event, on coming back to the front, and before every save). The page gets `paydayNativeEvent("import", text, true)` (or a reason with `false`), checks it again, moves focus to a confirmation with what's in the file, and changes nothing until "Replace with this backup". Just before anything replaces the data (an opened file, a pasted backup or an automatic backup), the current data is saved as a kept backup (`-keep`, kept 30 days whatever follows). A file from another phone never changes this phone's notification or appearance settings (a restore never changes notification settings). Settings › Backup, export & restore › "Import a backup file…" uses the system file picker (`ACTION_OPEN_DOCUMENT` through the Activity Result API) and the same path. It's a copy, not sync. Dovetail leaves itself out of its own share sheet.

## Exports
Settings › Backup, export & restore:
- "Share for analysis" (`exportMarkdown`): `dovetail-analysis-<date>.md`, with a preface explaining the model (people → accounts → "leftover goes to", budgets, savings, one-offs, ticks, budget months, the payday rule), the household and money flow, bills, budgets, savings transfers, other income, saved months, the Analysis figures (average month, categories, the next 12 months' outgoings and projected float, saved so far, price changes, top-ups) and the app version. "Copy report" copies the same text.
- "Share spreadsheet (CSV)" (`exportCsv`): `dovetail-bills-<date>.csv` and `dovetail-months-<date>.csv`, shared together (`ACTION_SEND_MULTIPLE`). Text that a spreadsheet would read as a formula is prefixed with an apostrophe.
Every figure comes from the functions the app uses. In a browser the buttons download the files instead.

## Reminder notifications
Off until switched on in Settings › Reminders & notifications (only in the Android app). Switching on asks for `POST_NOTIFICATIONS` (Android 13+); if it's refused the switch stays off with how to allow it. What's notified, worked out by `notificationSchedule(c, months, today)` for the next 90 days: "Payday tomorrow" (with the number of transfers, and with amounts on, "Expected left over"; needs a payday), each bill renewal and reminder on the day it becomes due soon (its remind-me time) and on the day, and each dated one-off the day before. Amounts only if "Show amounts in notifications" is on; on a locked screen Android shows "You have a reminder" unless the phone allows sensitive notifications there. The page sends the schedule (`setNotificationSchedule`) 2 s after any change and on every start. The time is between 06:00 and 22:00, clear of midnight. The app runs a daily WorkManager job (inexact; no exact-alarm permission) from the chosen time, and every run also books a one-off run for the next chosen time, because the daily job drifts later: a run more than an hour early books today's and posts nothing; otherwise it posts that day's entries that haven't been posted and books tomorrow's. Switching on (or changing the time) after today's time posts today's entries straight away. Each entry also carries a "late" wording for the next day ("Payday today", "Yesterday, …"): if Android only gets to run the check the following day (it can delay apps that aren't opened often), the missed entries go out then in that wording, never from before notifications were switched on. It does nothing while switched off or not allowed. One channel, "Reminders". Tapping a notification opens Reminders. WorkManager reschedules the job after a restart.

## Bridge (`window.PaydayNative`)
`saveBackup(json)`, `keepBackup(json)`, `listBackups()`, `readBackup(name)`, `share(json, fileName)` (backups only), `shareFiles(json)` (exports: one or two text files), `shareText(text, title)` (2.7: the month's transfers as a plain-text message, at most 20,000 characters), `sendFeedback(subject, body)` (2.9: opens the email app with a message to the support address, `FEEDBACK_EMAIL` in `MainActivity.kt` and `export.js`; at most 20,000 characters; with no email app, a message gives the address), `pickBackupFile()`, `lockAvailable()`, `lockEnabled()`, `setLockEnabled(on)`, `setTheme(theme)`, `haptic(kind)`, `setNotificationsEnabled(on)`, `notificationsEnabled()`, `notificationsAllowed()`, `setNotificationSchedule(json)`. Results come back through `window.paydayNativeEvent(type, value, ok)`: `"lock"`, `"notify"`, `"import"` (a backup file's text, or a reason) and `"open"` (`"due"`, from a notification). Absent in a browser, where the page works without it. Only the bundled page can load (other navigation is blocked).

## Permissions
- `USE_BIOMETRIC` for the optional app lock (normal permission, granted at install, no prompt).
- `uk.whiteboard.payday.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`, added by AndroidX Core: an app-private permission used internally on Android 10–12; it grants nothing to anyone else.
- `POST_NOTIFICATIONS` (2.2), only asked for when reminder notifications are switched on.
- `RECEIVE_BOOT_COMPLETED` and `WAKE_LOCK`, added by WorkManager for the daily reminder check so it survives a restart. Both are granted at install without a prompt. WorkManager's `ACCESS_NETWORK_STATE` and `FOREGROUND_SERVICE` are removed in the manifest (Dovetail never uses them).
- No INTERNET, no network state, no storage, no camera, no contacts, no exact alarms. Opening and importing files uses content links and the system picker, which need no permission. `build.sh` fails if INTERNET ever appears.

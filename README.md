# Dovetail

Dovetail (called Payday up to version 2.8) is an offline Android app for households (one person or several, most often a couple) who run their money across more than one bank account. It does one job, the payday routine: you type in the take-home pay that arrived, and it works out the transfers between your accounts, in order, so every bill, spending budget and savings transfer is covered. It works out what each person pays into anything shared, under the arrangement the household has chosen (pooling everything, sharing a joint account, one person paying the bills, each paying certain bills, or someone paying board), then shows what's left over (the "float" in the code and data) and whether any account will be short. Around that job it has an Analysis tab (how the months ahead look), Reminders (bills that don't come every month, and renewals), optional notifications, backup files that open on another phone, and exports, and it leaves earlier months as they were when things change. It deliberately doesn't connect to banks or the internet (no INTERNET permission), track what's actually spent, budget by category, move money, give financial advice, keep a tally of who owes whom, or track net worth. Pay can come monthly, every four weeks, every two weeks or weekly; the transfers are made once a month. For now it works in pounds and UK tax years, and is edited on one phone (a second phone can be brought up to date with a file). Package `uk.whiteboard.payday`.

Nothing about any household is built in: everything comes from what's entered. A new install starts with a seven-step setup.

## Layout
- `web/`: the whole UI.
  - `template.html`: HTML and CSS (design tokens at the top), with a `/*PAYDAY_SCRIPTS*/` marker.
  - `src/calc.js`: money, date and payday helpers (with England and Wales bank holidays by rule, 2.16.1), pay patterns and counting paydays (2.16, 2.17), the household tree, the transfer calculation, bill categories, tax years.
  - `src/migrate.js`: data upgrades (1.x → schema 5).
  - `src/analysis.js`: Analysis figures, the reminder list, the notification schedule.
  - `src/export.js`: Markdown and CSV exports, Share text, feedback email.
  - `src/ui.js`: the page (DOM, storage, Android bridge, charts). The other four are pure functions with unit tests.
  - `fonts/`: Figtree and Bricolage Grotesque (OFL).
- `app/`: the Android app (Kotlin).
  - `MainActivity.kt`: WebView on `file:///android_asset/index.html` (if its renderer crashes, a new WebView replaces it and reloads the page; the WebView is destroyed with the screen), edge-to-edge insets (refreshed on every resume), Back, app lock, theme, share sheet, opening backup files, notification permission.

  - `OpenFileActivity.kt`: receives a backup file opened or shared from another app.

They run with `SIM_FIGURES=1` (`0` switches them off; the default is `FIGURES_DEFAULT` in `logic.mjs`), and `node sim/analyse.mjs --figures` reports how far the figures are from the truth and how often an account is short. Not covered yet: ticks, and typed or estimated pay from saved months; two changes in a row (one replacing a later one) and "Delete account…" closing an account; the screens of a change (the order of answers); and backups or update files between versions. `ui.mjs` types households into the real setup screens in Chromium (taps, messages, defaults that had to be changed, the preview and Pay tab against `calc`) and `analyse.mjs` sums it up: `npm run sim:ui` (the full run: 360 households, about 4 minutes; `node sim/ui.mjs 40 && node sim/analyse.mjs` is a 30-second check). - `build.sh`: page, web tests (installing Playwright's Chromium first if it's missing), JVM tests, lint, signed APK and app bundle, checks (no INTERNET, no permission off the allowed list, both signed with the release certificate). `tests/build-page.mjs` builds the page without the Android SDK.
- `.github/workflows/ci.yml`: everything `build.sh` checks, on every push. On `main` it also signs the APK and AAB with the repository secrets, checks both certificates, attaches `Dovetail-v<version>` (the `.apk` and `.aab`) to the run and publishes them as the GitHub Release `v<version>`.
- `CONTRIBUTING.md`: the rules for everyone. `PRIVACY.md`: the privacy policy (for Google Play). `SECURITY.md`: how to report a problem.
- `tools/make-store-art.mjs`: the Google Play icon (512×512) and feature graphic (1024×500) as PNGs, made from `MARK` and the chart colours, in `build/store-art/` (not committed).

Gradle's `:app:generatePaydayPage` builds `app/build/generated/payday-assets/` before every build: `index.html` is `template.html` with the five scripts inlined in order inside one function scope, plus `fonts/`. It fails if a script contains `</script`. Nothing generated is committed.

## Building
Needs JDK 21+ (for Robolectric; the app compiles for Java 17), Node 18+, Android SDK platform 36 and build-tools 36.0.0.
```
export ANDROID_HOME=/path/to/android-sdk
export PAYDAY_KEYSTORE=/path/to/payday-release.jks
export PAYDAY_KEYSTORE_PASS=...
./build.sh
```
- Output: `app/build/outputs/apk/release/app-release.apk` and `app/build/outputs/bundle/release/app-release.aab` (Google Play), same key (alias `payday`). `build.sh` checks the certificates match and neither has INTERNET. Updates only install over the top with the same key.
- `settings.gradle.kts` lists Google's Maven Central mirror first (Maven Central can return HTTP 429 to shared machines); Robolectric uses it too.
- Each release: bump `versionCode`/`versionName` in `app/build.gradle.kts` and `VERSION` in `web/src/ui.js`, add the version's "What's new" lines to `WHATS_NEW` in `ui.js` (keyed by version; they name any change to an existing household's figures), add a CHANGELOG entry.

## How the transfers are worked out
- Per account: in = pay of the people paid into it (typed, or estimated from the last month that has it, or usual pay as it was that month: 2.15, `personAt`) + other income + one-off income. Out = bills due that month + bills not listed yet (below) + budgets + savings transfers + one-off payments.
- **A rough figure for an account's bills (2.14, `docs/onboarding.md` 5.2)**: an account can have a figure for its bills instead of every bill being listed (`estimates`). Each month, *not listed yet* = the figure less the account's listed bills that come in 7 or more months a year (`inFigure`: an empty `months`, all 12, or 7 to 11 of them), whether or not they're due that month, never below £0; it's money out of the account every month, on the account (`A[id].figure`, `A[id].unlisted`) and in its own total (`t.unlisted`, also `r.unlisted`; part of `billsExSav` and of the total out, so the figures still reconcile). Bills that come in 6 or fewer months a year always count on top. So listing a monthly bill within the figure changes no transfer; a bill that comes 7 to 11 months a year lowers the months it skips; a bill that takes the listed bills past the figure adds exactly what's past it. Two figures on one account add up. With no figure, nothing changes. `estimateTotals`, `estimateParts` in `calc.js`.
- Each account sends its leftover to another (`leftoverTo`) or keeps it. Working up from the accounts nothing sends to, a subtotal is the account's in − out plus what its children pass up. Positive goes to the parent; negative is a top-up from the parent; an account that keeps its leftover holds its subtotal as the float. Settings won't allow a loop.
- **Shares (2.12)**: an account can be paid for by people (`funding`): each pays from their pay account. Set amounts (or a percentage of that month's pay) are paid whatever the account needs; what it still needs (its own costs, less its own income and what its branch passes up) is shared among the others by the rule: `equal`, `pay` (each person's usual pay, or this month's when there's none), `afterOwn` (what each person's own account has left after its own bills), `sameLeft` (so everyone keeps the same; someone who'd keep less pays nothing) or `set` (set amounts only). Shares are to the penny, any rounding penny to the largest. Someone paid into the account itself pays their share by leaving it there; someone whose pay already reaches it through what's left is left out (Settings warns). Funded accounts are worked out deepest first. With no `funding`, nothing changes. `fundingShares`, `pennyShares`, `sameLeftShares` in `calc.js`.
- Order: shares first, then surplus transfers deepest first, then top-ups from the top down, then savings transfers.
- Step ids (used for ticks): `c:<personId>><accountId>` (a share), `t:<from>><to>` and `s:<savingsId>`.
- **Months use their own arrangement (2.12)**: every calculation goes through `cfgFor(c, k, oneOffs)` (`calcMonth` for a saved month), which applies the change in effect for month k (below). With no changes it returns the settings themselves.
- **Set amounts first, top-ups from money that's there, board (2.12.1)**: accounts paid for only by set amounts are worked out before the others, so "keep the same" sees money an earner sends a partner. Money a bill payer sends from their own (funded) account as a set amount is theirs, not part of what the others share. A top-up sends only what its account has by then (`short` on the step; `cant` lists those with nothing to send) and the rest stays a shortfall in the account that needed it (a float with `short: true`): in households with shares since 2.12.1, and in every household since 2.13 (the owner's decision), so no transfer is listed from an empty account. Months where the money is there are as before. A boarder's own account (`boarderAccounts`: a person with `boarder: true` paid into it, nobody else, keeping what's left, nothing passing into it and nobody else paying shares into it) is `outside`: not in `floats`, `flt` or the totals, and their board counts as money in (`t.board`).
- **Short (2.13: one meaning everywhere)**: a month is short when any account that keeps what's left (any float; a boarder's own account isn't one) ends it below zero. `shortAccounts(r)` lists them with the shortfall, `isShort(r)`, `shortNamed(r)` (more than one float, so the short ones are named rather than the total said) and `shortWords` in `calc.js`; the Pay tab, setup's preview, Analysis and the exports all use them. The total (`flt`) stays the headline figure. With one account keeping what's left, this is exactly the old "the total is below zero". `personKeeps(c, r)` (what each person's own account keeps) is in `calc.js` too.
- Reconciliation: total floats = total in − total out. If not (say a bill points at a deleted account), the hero shows a warning and "Open accounts" (`#check`).
- On screen the words are plainer (float is "left over", budget month is "pay month", projected is "estimated"); code, data and exports keep the old names.

## Data
Everything is in WebView localStorage for the origin of `file:///android_asset/index.html`. **Don't change that URL** (for example to WebViewAssetLoader's https://appassets.androidplatform.net) without a migration: a different origin starts with empty storage.

- `payday.config.v1` (schema 5):
  - `people` {id, name, payAccount, usualPay, boarder?, was?} (`boarder: true`, 2.12.1: pays board and keeps the rest; kept only when true; `was` (2.15, optional): [{until: "YYYY-MM", usualPay}], oldest first, the person's usual pay up to and including `until`, written when an edit to usual pay is dated (`datePersonEdit`) and read through `personAt`/`cfgFor`, and by `payEstimate`'s usual-pay fallback, so earlier months keep the pay they had; `normCfg` keeps an entry only with a valid month and an amount of £0 or more ("an earlier pay that couldn't be used"), sorted, one per month; people aren't in `ITEM_DATED`, `docs/payperiods.md` 11.1); `pattern` (2.16, optional) {every: 7, 14 or 28, each}: paid every week, two weeks or four weeks, `each` the usual take-home pay each time (above £0, at most £1,000,000, to the penny; anything else is dropped as "a pay pattern that couldn't be used"); with a pattern, `usualPay` is always `usualMonthly` (each × 52, 26 or 13 ÷ 12), so everything that reads usual pay (shares in proportion to pay, Analysis) uses pay over a year ÷ 12; a change of pattern is dated like usual pay (`was` entries may hold `pattern`); unknown keys inside it are kept; 2.17 (`docs/payperiods.md` 13.2): `pattern.on` (optional, "A recent payday": any payday in the series as it usually falls) and `pattern.since` (optional, a first pay: paydays before it aren't counted), real dates from 2000 to 2099 (`paydayDateOk`; a bad one goes on its own, and `since` without `on`, "a payday date that couldn't be used"); they're corrections, never dated: `personSnap` and `was` entries hold only `{every, each}` (`patternCore`; `normCfg` strips them from a `was` entry), and `personWas` gives an earlier month at the same interval today's `on` (not `since`); `accounts` {id, name, colour, leftoverTo, funding?, closedFrom?}.
  - `funding` (2.12, optional) {people: [personId…], rule: equal/pay/afterOwn/sameLeft/set, set?: {personId: {amount} or {pct}}}. `closedFrom` (2.12): "YYYY-MM", the change that closed it.
  - `flows` (2.12, optional): changes of how the household manages its money, oldest first: {from: "YYYY-MM", was: {accounts: {accountId: {leftoverTo, funding?}}, pay: {personId: accountId}}}. The settings hold the latest arrangement; a month before a change uses that change's `was`. An account not in a `was` hadn't opened yet, and is left out of that month unless something that month uses it. `was.items` ({bills, budgets, savings, income}: {itemId: accountId}) says where items the change moved were (`itemsAt`; the earliest change after a month wins), and `was.names` the names and colours it changed (for Undo). `was.boarders` (2.12.1, when the change asked about board): who paid board before it; `cfgFor` gives earlier months those flags. `applyChange`, `removeLastChange`, `arrangementAt`, `accountRoles` in `calc.js`.
  - Dated items (2.12, stage 4, optional): on a bill, budget, savings transfer, income or (2.14) rough figure, `was` [{until: "YYYY-MM", amount, account (fromAccount for savings), months (bills)}] (oldest first; until = the last month those values applied) and `start` ("YYYY-MM", the first month it counts). `ended` {bills, budgets, savings, income, estimates: [item + ended "YYYY-MM"]}: items deleted (or a figure ended by "That's all of them"), still counted before that month. `cfgFor` gives each month its items (`itemAt`, `allItems`). Edits are dated only when there are months saved before the pay month the app opens on (`hasHistory`): `dateEdit`, `undateLast`, `endItem`, `unendItem`.
  - `bills` {id, name, amount, account, months, renews?, lead?, note?, savings?, savingsSince?, category?, categoryAuto?, history?: [{on, date, from, to}]}.
  - `estimates` (2.14, optional) {id, account, amount}: a rough figure for an account's bills (on screen "rough figure", and what it has over the listed bills "not listed yet"). A dated item like the others (`was` [{until, amount, account}], `start`, `ended.estimates`), so earlier months keep their figures, "That's all of them" is an ending with Undo, and a change of style moves a figure with the account's bills (`was.items.estimates`). `normCfg` keeps an entry only with an id (each once), an account in the household (closed ones too) and an amount of £0 or more ("a rough figure that couldn't be used"), and stores the list only when there's one, so every other household's settings stay exactly as they were. Start again clears it with everything else.
  - `income`, `budgets`, `savings` {id, name, amount, fromAccount, since?} (`since`: the budget month Saved so far counts it from), `reminders`, `payday` {day: 1–31 or "last", weekend?} (empty means not set; `weekend: false` is the unticked box. `paydayIn` caps the day at the month's length; "last", and a numbered day unless `weekend` is `false`, then moves to the working day before a weekend or an England and Wales bank holiday (2.16.1: `easterSunday`, `bankHolidaysEW`, `isBankHolidayEW`, `isWorkingDay`, `workingDayOnOrBefore`, worked out by rule, so one-off holidays such as a jubilee or a coronation, and Scotland's and Northern Ireland's, aren't known); a payday on the 15th or later, or "last", pays for the next month), `doneLog`, `setupDone`, `example` (example household only).
  - Optional, defaults in `normCfg`: `appearance` {theme: system/light/dark, textSize: small/normal/large}, `notify` {on, time "HH:MM", amounts}, `lastVersion` (for What's new), `setupTips` (true shows "Finish setting up"; missing means off), `tourDone` (false until the tour has run; missing means seen). `normCfg` keeps those last two only when they say something, so an existing household's settings never change.
- Bill categories: housing, utilities, insurance, transport, children, health, subscriptions, memberships, debt, savings, other. A suggestion from the name has `categoryAuto: true` and follows renames; one the user picks (including "Not categorised", `""`) is never overridden. The Savings category and the savings tick are kept in step.
- `payday.months.v1`, per budget month: `pay` {personId: amount or null}, `payEstimated`? {personId: true} (that pay is the estimate filled in when a transfer was ticked before pay was typed; removed when the box is typed in; a month without it reads as before), `done` {stepId: amount when ticked}, `oneOffs` [{id, kind "out"/"in", name, amount, account, date?}], `results`, `updatedAt`. `extra`? (2.16) {personId: {amount, counted?}}: an extra payday for someone on a pattern, set aside (left in their account, out of the transfers) unless `counted`; it applies only to typed pay; `normMonths` keeps unknown keys inside an entry and drops one it can't read ("an extra payday that couldn't be read"). 2.17: `extra[id].edited` (kept only as `true`: an amount the household typed, or "Not an extra payday", `{amount: 0, edited: true}`), so the default isn't rewritten; `paydays`? {personId: 0–6}: the count frozen when that person's pay was first typed or ticked while they had a payday date ("a payday count that couldn't be read"; an empty one is dropped); a one-off's `extraFrom` ("YYYY-MM") and `extraOf` (a person id), written by "Use it this month", kept as a pair or both dropped ("an extra payday used later that couldn't be read").
- `payday.wealth.v1`: the old Wealth tab's data (balances from 1.x). Never used, and never changed by an upgrade or a restore; kept in every backup while it's there. 2.13, one-off: Settings › Backup, export & restore › **Old Wealth data** (shown only while it exists; `wealthBox`) says backups and update files include it, and "Save the old Wealth data as a file, then remove it" shares it as `dovetail-wealth-<date>.json` (`wealthFile`; `shareFiles`, or a download in a browser), then "Remove the old Wealth data" (two taps) keeps a backup of everything with it first (nothing is removed if that fails) and removes the key. Backups then leave it out, and the settings say it was removed (`wealthRemoved: true`, optional, kept by Start again), so nothing brings it back by itself: an update file from the other phone, an opened file, a pasted backup and the recovery screen restore everything else but not a file's Wealth data (`wealthGone`). Without that, a restore adds a backup's copy only when the phone has none.
- `payday.errors.v1`: the last ten unexpected errors (never names or amounts), listed in "Copy app details". `payday.broken.v1`: one copy of data the recovery screen set aside; Settings › Backup can copy it out or remove it.
- `migrate(c, m, w)` runs on load and on restore; each step is idempotent.
  - 1.x data (schema 3 and older, `looksLegacy`) becomes editable people and accounts in the old built-in shape, keeping the account ids so bills need no change. Accounts get plain names ("Current account 1", "Current account 2", "Joint bills account", "Joint spending account"); people come from the data (`legacyPeople`: defaultPay's keys, then the months' pay fields; `nameFromKey`). Ticks are renamed, the overdraft becomes a one-off, mortgage deal ends move onto the mortgage bills.
  - Schema 4 → 5 suggests bill categories.
  - 2.12 adds no upgrade step: `funding`, `closedFrom` and `flows` are optional. `normCfg` drops anything unusable in them (an unknown rule, people not in the household, negative set amounts, a percentage over 100, a bad month), and stores `flows` only when there's a change. From 2.13 a restore says so (below); people who have left the household are dropped from a share's list without a word, since removing someone in Settings leaves them there. A phone on 2.11 ignores them (no shares, so a joint account others pay into shows as short), and a phone on 2.12 ignores `boarder` (2.12.1) and works set amounts in the old order. From 2.13 a file from such a household is version 6, which those phones refuse (see Backups and restore); files written by 2.12 and 2.12.1 are version 5 and still open on them, so update both phones to the same version first.
- `normCfg` and `normMonths` check settings and months item by item on open and restore: a payday day that isn't 1–31 or "last" counts as not set, bill months are whole numbers 1–12, non-object items are dropped, badly shaped ticks, pay and one-offs are fixed. A negative amount on a bill, budget, savings transfer or income is kept in the data as `badAmount` and the amount counted as £0 (`badAmount` goes once the item has an amount again). A month whose key isn't a real "YYYY-MM" is kept but left out of the calculations (`validMonth` in `payEstimate`, `hasHistory`, `usedMonths`, `typedPayMonths`, `avgIncome`). Sound data passes through unchanged.
- **What couldn't be used (2.13).** Both take an optional list and add a plain description of everything they drop or fix ("a bill with a negative amount (counted as £0)", "a change of style with a bad month", "a share rule Dovetail doesn't know", "a month with a bad date (left out)"…), never a name or an amount; sound data adds nothing. After a restore or an opened file the message is "Backup restored." (or "Updated") plus one sentence, `reportSentence`: "Some things couldn't be used: …" with each kind once, at most three, then "and N more". The error log gets the same sentence once. On the first open of a new version the same check runs on the stored data (which is kept as a backup exactly as stored first: see Backups and restore), and if it finds something the sentence shows once and goes in the error log. After the recovery screen restores a backup, the sentence shows once the page has reloaded (`payday.note` in sessionStorage).
- Recovery screen: if saved data can't be read or opening it throws, "Dovetail couldn't open" replaces the app: restore an automatic backup, open a backup file, start again (two taps) or copy app details. The data is set aside first (if it can't be, nothing happens). Unreadable data is never treated as a new install.
- Saving: pay and one-offs 0.7 s after the last change, settings 0.6 s; at once when the app goes to the background.
- The page never saves over newer data: if storage changed underneath it (another copy of the page) it takes the newer data instead (on the `storage` event, on coming to the front and before every save).
- Android settings (SharedPreferences `payday`): `app_lock`, `theme` (applied to the window before the page loads), `notify_on`, `notify_schedule`, `notify_posted` ("date|key" already shown, kept 100 days).
- Android backup (`allowBackup=true`): only `files/backups/`, only when end-to-end encrypted (`backup_rules.xml` for Android 10–11, `data_extraction_rules.xml` for 12+). A fresh install that finds backups offers the newest in setup.

## Backups and restore
- Format (Copy backup, Share, update files, automatic and kept backups): `{"app":"payday-transfers","version":5,"savedAt":…,"config":…,"months":…,"wealth"?:…}`, months copied as they are.
- **Version by content (2.13, `backupVersionFor`, `backupJson` in `calc.js`).** A file is version 6, with `"needs":"2.13"` straight after the version, when the settings use anything a phone before 2.13 would misread or drop: an account with `funding` or `closedFrom`, any `flows`, a person with `boarder`, or a dated item (`was`, `start`, `ended`). Otherwise it's version 5, byte for byte as 2.12.1 wrote it, so a pooled household's files still open on any phone from 2.0 on. **2.14:** a file whose settings have a rough figure (`estimates`, or one in `ended.estimates`) is version 6 with `"needs":"2.14"` (`backupNeedsFor`), so a 2.13 phone refuses it with "This file needs Dovetail 2.14 or later" rather than drop the figure; one that uses only 2.13 things still needs 2.13. Phones before 2.13 refuse version 6 with their own "made by a newer version" message rather than show different figures. **2.15:** a file where anyone's usual pay is dated (`people[].was`, `hasPersonDated`) is version 6 with `"needs":"2.15"` (`DATED_PAY_NEEDS`); `backupNeedsFor` gives the highest that applies. **2.16:** a pattern now or in a `was` entry needs 2.16. **2.17:** a recent payday (`pattern.on`, `hasPaydayDates`), or a month with a one-off marked `extraFrom` (`extraUsedLater`), needs 2.17 (`PAYDAY_DATE_NEEDS`); `backupVersionFor(c, months)` and `backupNeedsFor(c, months)` take the months as an optional second argument (`backupJson` and `keepRaw` pass them). Counts and amounts need nothing more: a 2.16 page reads a frozen month's figures the same. The rule for later versions: a new field (or a new key inside `funding`, `flows` or `was`) that changes figures, or that an older page would drop, raises the version a file needs **when that field is present**.
- The page opens files up to version 6 (`BACKUP_VERSION`). It refuses a later version, and a version 6 or later without `needs` (no Dovetail writes one), with "This backup was made by a newer version of Dovetail. Update the app first."; and a file whose `needs` is a later app version than its own with "This file needs Dovetail <needs> or later. Update the app first." (`backupRefusal`), on every path (paste, automatic backup, opened file, recovery screen). Nothing changes.
- A restore is tried on copies first (including the month to open on) and refused before anything is saved if it can't be opened. Pasted text over 2 MB, or from another app, is refused. Any earlier version restores through the same migration.
- A restore never replaces Wealth data already on the phone and never changes notification settings. A backup file opened from another app also keeps this phone's appearance (a pasted or automatic backup brings its own back).
- Just before anything replaces the data, the current data is kept as a backup (`-keep`, `keepCurrent`). For an opened file (Update, "Replace with this backup"), a pasted backup, Restore on an automatic backup in Settings and Start again, anything being typed is saved first and, if the kept backup fails, nothing changes ("Couldn't save a backup, so nothing was changed."). Setup's restore offer has nothing to keep and carries on.
- A pasted backup is described before the second tap, as an opened file is (`backupSummary`: when it was saved, people, accounts, bills, saved months); a file this page would refuse is refused at the first tap.
- **The first open of a new version** (`lastVersion` isn't this version; also 1.x data) keeps a backup of the settings, months and Wealth data **exactly as they were stored** (`keepRaw`), before `migrate` or the new `lastVersion` writes anything, so whatever a new `normCfg` or `migrate` changes can be brought back.
- Automatic backups: `files/backups/backup-YYYYMMDD-HHMMSS.json`, 2.5 s after the last change (or on going to the background), skipped when nothing changed, never for the example or before setup. Kept (`BackupStore.prune`): the 10 newest, the newest per day for 14 days, the newest per calendar month for 12 months, and `backup-…-keep.json` for 30 days (the newest 20; 5 before 2.13).

## Opening backup files (Android)
- `OpenFileActivity` (no screen) takes `ACTION_VIEW` for `application/json` and `text/plain` (some apps label .json as text) and `ACTION_SEND` for `application/json` only (`text/plain` would put Dovetail in every share menu). Payday backups open too.
- It reads only `content://` links, while it holds access (no storage permission), and refuses files over 2 MB or that aren't backups.
- Hand-over to MainActivity: a private file (new name each time, written before it appears, read once), with NEW_TASK | CLEAR_TOP | SINGLE_TOP so the open Dovetail receives it.
- Launch modes, on purpose: MainActivity keeps the normal mode, so tapping the icon never closes a file picker, permission prompt or share screen. Hand-over and notification intents are MAIN/LAUNCHER like the icon's, so they land in the same task; a second MainActivity started on top closes itself. Reopening from Recents (FLAG_ACTIVITY_LAUNCHED_FROM_HISTORY) is ignored.
- The page gets `paydayNativeEvent("import", text, true)` (or a reason with `false`), checks it again and shows what's in it; nothing changes until "Replace with this backup".
- "Import a backup file…" uses the system picker (`ACTION_OPEN_DOCUMENT`, Activity Result API) and the same path. It's a copy, not sync. Dovetail leaves itself out of its own share sheet.
- **Updates from the other phone.** A file whose settings share an account id with this phone's (`sameHousehold`; ids are random, so separate households never match) is this household brought up to date. On a set-up phone (not the example) it's the first notice on Pay (`#updateOffer`): "Update from this file?", when it was saved, **Update** or Cancel. If a month here was saved after the file (`changedSince`: its `updatedAt` is later than the file's `savedAt`) it warns and Update turns red. An open tour or sheet closes first. Update does the restore above, then shows "Updated". Other households, "Import a backup file…", the example and a new install get the full confirmation. One way: the receiving phone's changes are replaced.

## The Pay tab
- **Pay patterns (2.16, `docs/payperiods.md` 5.3 and 11.2).** One routine a month stays, on the household's payday setting, called the **transfer day** wherever someone has a pattern (`dayWord`; monthly households keep "payday" everywhere). A transfer day is required once anyone has a pattern. **One figure everywhere:** `planPay(c, months, k, live)` gives each person's `arrived`, `setAside` and `used` for a month (`live`: the unsaved boxes), and the Pay tab, `flushMonth`'s results, setup's preview, `predictedFloat`, `projectedFloat`, `averageShort` and a change of style all use it; `payFor` is `used`. Someone on a pattern types everything that arrived since the last transfer day; until then the plan is pay each time × the paydays every month has (4, 2 or 1), never an earlier month's total. Once their pay is typed, "Had an extra payday?" opens one amount (pre-filled with pay each time), set aside unless "Count it this month": set aside never moves a share; counted moves shares only under "after own bills", "so we each keep the same" and a percentage of pay. If anything is ticked, the line opens counted; setting it aside then takes two taps with a warning; a ticked step that went down says "…, £64.80 less. Move £64.80 back to Current account, or untick and tick again once it's right." (every household). **Standing orders** (`standingOrders`): for each share, top-up or savings transfer out of an account only that person is paid into, the largest amount over this month and the next 11 ÷ 4, 2 or 1, rounded up (four-weekly only when it varies; never a move of what's left, where Settings › People says why: `moveTo`); listed in Settings › People, and on the Pay tab once (`standingOrdersNotice`: the first month on a pattern or a new interval, and when a figure goes up), worked out, never stored.
- **Counting paydays (2.17, layer 2, `docs/payperiods.md` 13.2).** With a recent payday (`pattern.on`), a person's paydays are `on` + j × `every`, each moved to the working day before a weekend or England and Wales bank holiday (`workingDayOnOrBefore`, as the transfer day is), and month k's are those after the transfer day before it, up to and including its own (`transferWindow(c, k)`: `{after, upTo}`, the 25th unmoved without a transfer day; `paydaysIn(pattern, after, upTo)`; `paydaysFor(c, pid, k)`; in the window that holds `workingDayOnOrBefore(since)`, a payday counts from that day; a window that ends before it counts as if there were no `since`, since earlier months get the pattern only by "Change earlier months too"). Windows run 24 to 35 days, so a month has from N − 1 to N + 1 paydays (four-weekly: 0 to 2). **Typed months never move:** a month's figures come only from what's stored in it (pay, `payEstimated`, `extra`), as 2.16 reads them. `planPay(c, months, k, live, opts)`: an empty box with a date plans on each × min(M, N), nothing set aside (M: the stored count, else today's), so a month with fewer paydays plans on what arrives; a layer-2 entry adds `layer: 2`, `m`, `dates`, `expected` and `extraDefault` (other entries are 2.16's); `opts.typical` plans on each × N whatever the count, which `standingOrders` and `averageShort` use, so standing orders are the same with or without a date. **The freeze** (`freezePaydays(c, months, k, body, old)`, called on each save and each keystroke): when a person's box goes from empty to a figure while they have a date and no count is stored, `paydays[id]` is stored and, with more than N, `extra[id] = {amount}` with the default r2(A × (M − N) ÷ M) (A: the typed pay, or each × M when a tick filled the box); whenever the count is above N and the extra has no `edited` and isn't used later, its amount follows the pay in the box. That line opens by itself (`extraState`: "freeze"), never counted, with "Not an extra payday" in place of Remove. A line that's already there when a month is frozen (opened from "Had an extra payday?", perhaps before the date) is the household's own: the freeze marks it `edited` and never rewrites it. A change of interval freezes again only the months it reaches that already had a count (`intervalChangedMonths`, `refreezeInterval(after, months, pid, keys, before)`), clearing a line only when the old count opened it; a household without a date is never touched. **"Use it this month"** (`useExtraOffer`): in a month with fewer paydays than usual, after a month whose extra was set aside, it adds that amount as one-off income marked `extraFrom`/`extraOf`; while it exists the earlier month's line is locked (`extraLock`). Easter 2027, weekly on Mondays with the transfer day on the 25th: April has 5 paydays (£420.00 set aside), May 3 (£240.00 short, £180.00 left over with April's extra used).
- From the top: month bar; at most one notice (`#notice`, `renderNotice`: an update file, a restore offer, What's new (the lines of every version since the one last opened, newest first: `whatsNewVersions`), or the example banner / "Finish setting up"); the hero; the reminders nudge (`#actionBanner`); take-home pay; the transfers with "N of M done" (2.13: "All transfers done", the ring's "done" and the phone's "done" tap come only when no ticked transfer has a difference still to send; otherwise the ring says "ticked", and with every transfer ticked `#unsettled` says how much is still to send) and **Share** (`#shareTransfers`); a line when non-monthly bills are due (`#nmNote`); **This month in detail** (`#payDetails`: Not every month, one-offs, each account's figures, totals); Bills by account.
- This month in detail is closed, but opens by itself in a month with one-offs, until opened or closed by hand (kept for the session: `payDetailsOpen`, not saved). A one-off's link and Reminders' "Open <month>" open it; the tour opens it and puts it back.
- **Share**: `transfersText(c, k, r, done, payInfo)` in `export.js`: each transfer in order with ☑ or ☐, "(top-up)", what's still to send if it changed since ticking, what's left over, and a line when pay is estimated. Sent with `shareText`; in a browser, the browser's sharing or the clipboard.
- **Update file**: in the app with a household set up (not the example), Share asks first ("Share this month", `openShareChoice`): "Send the transfers as a message" (the text above) or "Send an update for the other phone" (`shareUpdateFile`): the whole backup (`shareUpdate`) as `Dovetail-update-20-Oct-2026.json` (`updateFileName`, today's date), with the transfers as its message too (`updateText`; an email keeps it, but WhatsApp drops a message sent with a file, which is why it's a choice). Pending changes are saved first (`savePending`). If the file can't be prepared (over 2 MB, or can't be written) it says "Couldn't prepare the update file." The example household and a browser send the text straight away.
- **Shares (2.12)**: each is a transfer of its own, first, with "Alex's share (60%)", "Alex's share (half each)" or "Kit's board" under it (2.13: a percentage is of what the people sharing by the rule pay between them, so set amounts and board are left out; the equal rule says "half each", or "equal share" for more than two; someone paying board pays "board", never "a set amount"). When people's own accounts keep what's left, the hero adds what each keeps (`#heroKeeps`). The account cards list shares going out and coming in. The hero names any other account that's short (2.12.1, even when the whole month is short), a top-up that can't be made is a warning (`#cant_<account>`), not a transfer, and a boarder's own account has its own card after the household's, not counted in what's left.
- **Ticking before pay is typed** fills empty pay boxes with the estimate and marks them in `payEstimated`.
- **Rough figures (2.14, `docs/onboarding.md` 5.6 to 5.8)**: under the first transfer into an account with a figure, "Includes £380 of bills not listed yet." (`#figNote_<account>`; `#figNote` under the transfers when none goes into it); the account's card in This month in detail has "Bills not listed yet"; Bills by account has "Joint: £1,120 listed · £380 not listed yet (your figure £1,500)" with a thin bar. Settings › Bills (`figBlock`, `#bf_<account>`) has the same line, "Adding bills won't change your transfers until they go past your figure.", the quiet "If Joint ran short before payday, the figure may be low.", Paste a list, Change the figure (a dated edit, with the usual "Changed from…" line) and That's all of them (ends the figure from this pay month, with Undo and the good news from `estimateEndEffect`: "All of Joint's bills are in. … Alex's share goes down by £100 a month and Sam's by £100."), and "Not sure you've got them all? Add a rough figure" on an account without one. Questions come once, when they matter, and nothing about them is saved: the listed bills going past the figure asks "Is that all of them?" (There are more rounds the figure up with `estimateRoundUp`); deleting a bill inside it offers "Lower Joint's figure by £30 too?" (`estimateDeleteOffer`); a price rise inside it is said in the toast, also after a renewal. A figure on an account a change of style has since made one a figure isn't offered on still counts, and Settings says so. No notifications, nothing on the top card.
- **Remind me** (`defaultLead`): when a renewal date is first set with no choice made, a week for a monthly subscription or membership, otherwise a month. A stored choice never changes.

## Analysis tab
- **Pay patterns (2.16):** someone on a pattern counts at their usual pay over a year ÷ 12 in the monthly picture ("Kerry's pay (about £1,690.00 a month: £1,560.00 every four weeks)"); estimated months use `planPay`; Pay and what was left shows the pay used, with what was set aside in its figures table. 2.17: someone with a payday date gets a measured average (`measuredPay`): typed pay ÷ the frozen count over their last 6 such months at the same interval (not months corrected with "Not an extra payday" or with an extra in a month that wasn't counted above usual), × paydays a year ÷ 12 (`incomeLabel`: "Jordan's pay (about £1,837.62 a month: an average of £424.07 a payday over 6 months)"); Month by month lists extra paydays and fewer paydays ahead in months not typed (`monthExtras(…).paydays`, `extrasText`: "Kerry: an extra payday, about £1,560.00 (set aside unless you count it)", "Marc: 3 paydays, not the usual 4").
Derived only: nothing new is asked for, and it can't see actual spending, so it judges the plan. Each chart has a key and a "Show the figures" table.
- **Month by month**: the float for 12 budget months (3 before the one on screen, that month, 8 after); a banner only when a month is short or there's no pay. `monthExtras` lists non-monthly bills and one-offs. The tightest month is the one with the biggest shortfall, then the least left.
  - Typed pay (`payIsTyped`, not in `payEstimated`) makes a month actual: solid, with a line at its predicted float (each person's latest earlier typed pay, or usual pay as it was that month). Others are estimated and hatched. Estimated pay is left out of averages, history and the predicted line.
- **The monthly picture**: savings rate, and income split into bills, budgets, savings and average left over. An account short in the average month (2.13, `averageShort`: each float over the 12 months from the month on screen, with typical pay) is named under it (`#anPictureShort`).
- **Where the money goes**: bills by category. - **Pay and what was left** (once two months have typed pay), **Saved so far** (ticked transfers and savings bills), **Price changes** (from bill `history`; hidden until there is one), **Accounts that ran short** (`topUps`; hidden when none): top-ups, and since 2.13 accounts left short: one that keeps what's left ending a month below zero while another kept money, a top-up that couldn't be made (`cant`) and the unsent part of a top-up (`short`), each kind explained in one line. - Charts are inline SVG (no libraries); keyboard readings go to a live region. Colours: `--viz-1`…`--viz-8`, separate light and dark.

Back keeps what's typed; nothing is saved until setup finishes. 2.15: the pay step says what to do if you're paid weekly, every two weeks or every four weeks (make the payday the day you'll do the transfers, and type the pay that's arrived since the last one), and that Universal Credit is the pay of the person it's paid to, typed from the statement each month. 2.16: the pay step asks "How often they're paid" per person (`#su_pf_<i>`: Every month by default, so a monthly household has no extra taps; every four weeks, two weeks or week makes the pay "Take-home pay each time" with "About £X a month over a year."); with anyone on a pattern, the payday step is "When will you make the transfers?", the transfer day, and can't be skipped. One person on a pattern who picks the pay account, bills account and spending account picture gets Bills topped up from the pay account, so a standing order shows (E17, `docs/payperiods/decision12.md`).
- **Finishing** (`setupResult`, `finishSetup`): "Looks right, start", "Finish later" or "Skip setup for now". The settings are made by one pure function, `setupSettings` in `calc.js` (2.13), from setup's answers and the settings there are now; the simulation builds its households with it too. Keeps what was entered; with nobody, one person "You"; with no accounts, one "Current account" that keeps what's left; incomplete rows are dropped with a message. Saves `setupDone`, `setupTips: true`, `tourDone: false`, `lastVersion`, keeps appearance and notification settings, backs up, starts the tour. Savings start (`since`) in the previewed month after "Looks right, start", otherwise `defaultMonth`.
- **Rough figures in setup (2.14)**: setup's answers can hold `figures` {accountId: a figure as typed} (blank or £0 is none). `setupSettings` keeps one only when it's above that account's listed bills that come in 7 or more months a year, and only where a figure is allowed (`estimateBlock`: not on a boarder's own account, nor on someone's own account when they pay a share into another under "in proportion to what's left after own bills" or "so we each keep the same", where it would move the cost to the others); otherwise it returns `figureNotes`, a sentence for each ("The bills listed for Joint account already come to £900.00, so its rough figure of £900.00 isn't needed."). A figure that isn't an amount counts as a row that wasn't complete. Without figures the settings are exactly as before.
- **The bills step (2.14, `docs/onboarding.md` 5.1 to 5.5)**: "Paste a list" (`#su_paste_open`) and "Not sure of every bill? Start with a rough figure" (`#su_fig_all`) at the top, and "How do I find my bills?" (`#su_find`: the help, one tap away). Each account's section has a running total ("Joint: 14 bills, £1,642.30 a month", `#su_b_<n>_tot`, a yearly bill as a twelfth) and "Not sure you've got them all? Add a rough figure for the rest" (`#su_b_<n>_fig`), or says why not where `estimateBlock` says no (`#su_b_<n>_nofig`). The figure box (`#su_figbox_<n>`, the figure `#su_fig_<n>`) asks in the design's words, with "Do this together…" for two or more people, "No bills from here" while nothing is listed (the section becomes a line saying so), and the check against what's moved in now (`#su_figin_<n>`, never saved): a figure well below it (by £20 and 5% or more) asks once, "Yes, it's bills" making the figure that amount. Suggestions: the six most common (rent or mortgage as one) and groups that open with a tap (`BILL_SUGGESTIONS`, `BILL_GROUPS`; with a figure open they're "Did your figure include…?"); someone's own account is a line with its own few (mobile phone, car finance, car insurance, gym). "Any bills that don't come every month?" (`#su_nm`, `NM_SUGGESTIONS`, no Council Tax) adds rows that are kept with their account's rows (`nm: true`), each with the account it's paid from. A household that lists everything sees two links and a running total, with no more taps than before. The preview says "Includes £380 of bills not listed yet." under the first transfer into the account (`#su_fig_note_<account>`), and `figureNotes` show there (`#su_fignotes`) and again after finishing.
- **Budgets and savings by account (2.14, 5.10)**: the spending and saving step is drawn by account ("Kept in Joint account", "Sent from Alex's account"; `data-acct`), so a row's account is where it's typed: the account shared spending goes to is open, and each person's own account (and any other that keeps what's left) is a line until something is added there. "Alex's spending money" is offered on each person's line when they pay into a joint account or one of them pays the bills. Rows in the shared account follow the answers; rows added in another account stay there (`picked`).
- **Paste a list (2.14, 5.4)**: `pasteBox`, in setup and Settings › Bills (next to Quick add, `#pasteBtn`, and from an account's figure): a plain text box (no clipboard permission) read by `parseBillLines`; "Found 18 bills, £1,642.30 a month. 2 lines need a look."; rows to check before adding, as Quick add's are (a bill already there unticked, a large amount flagged, an account named in the list matched by `pasteMatch` or flagged and put in the default, a yearly bill with no month asking for it); lines it couldn't read shown as they were pasted.
- **Finish setting up** (`#setupTips`): `setupChecklist(cfg, months)` in `calc.js` (pay, payday, bills, budgets or savings). 2.14: the bills item stays unticked while an account has bills not listed yet, as "List Joint's bills (£380.00 to go)" (`billsTip`, with `unlisted` per account). When all done or hidden, `setupTips` is removed for good. A restore brings back what the backup had.
- **Start again** (end of Settings › Backup; app only; not the example; two taps): saves, keeps a backup (`keepBackup`; if that fails nothing changes), clears the reminder schedule and the months, cuts settings to `{schema, appearance, notify}`, plus `wealthRemoved` if set (no `setupDone`; `payday.wealth.v1` untouched), and setup offers the backup back. App lock, notifications and appearance stay. Any settings without `setupDone` open setup.

## Look and feel
- Tokens in `web/template.html`, light and dark: `--bg`, `--surface`, `--sunk`, `--hair`, `--line`, `--ctl`, `--ring`, `--shadow`, `--r`, `--r-in`.
- `moneyEl()` shows smaller pence (textContent unchanged). `avatar()` badges get initials from CSS (`data-i`, `::before`), so screen readers and tests never see them. `renderHero` draws the hero.
- `animatePanel()` fades on tab change and slides on month change; `rollHero()` rolls the float; no animation under reduced motion. Ticking calls `haptic("tick" | "untick" | "done")` (no permission).
- Appearance: theme sets `data-theme` on `<html>`; text size sets `data-text` (root font size 0.9 / 1 / 1.15; all font sizes in rem). `setTheme` tells the app, which applies it to the window, lock screen and system bar icons on every start. Android's night mode isn't switched (it would restart the screen), so the splash follows the phone.
- The mark (2.11): money coming in (blue `--viz-1`, amber `--viz-4`) brought together and sent on (green `--viz-3`), stroked like the tab icons, on white. The same paths are in `MARK` (`ui.js`, drawn by `markSvg()` on the first setup step and in Settings › About, hidden from screen readers), the app icon (`ic_launcher_foreground`, a one-colour `ic_launcher_monochrome` for themed icons, white `ic_launcher_background`), the notification icon (`ic_stat_payday`, wider gaps) and the launch screen (`splash_mark`, dark colours in `drawable-night`); `mark.test.mjs` keeps them the same.
- Launch screen (Android 12+): `splash_mark_anim` draws the mark in about 0.6 s (the two streams, then the green shaft, then the arrowhead opens) on a circle in the card colour. `holdSplash()` keeps the first frame back until the animation has played and the page has loaded (`splashDone`: at least 700 ms, at most 1.5 s, never while the app lock is up, no wait for the animation when the phone's animations are off or a backup file is being handed over), then fades the launch screen out over 200 ms. Only on a fresh start, not a rotation or recreate.

## Reminder notifications
- **Pay patterns (2.16):** a household with a pattern gets "Transfer day tomorrow" ("Transfer day today" when late), with "Fri 30 Oct 2026 is for November 2026. …"; the Android channel description reads "Payday or transfer day tomorrow, bill renewals, your reminders and dated one-offs". No per-person payday notifications. Monthly households' notifications are unchanged.
- Off until switched on (app only), which asks for `POST_NOTIFICATIONS` (Android 13+); if refused, the switch stays off.
- `notificationSchedule(c, months, today)`, next 90 days: "Payday tomorrow", each renewal and reminder when due soon and on the day, each dated one-off the day before. Amounts only with "Show amounts in notifications" (2.13: "Payday tomorrow" then also names an account that will be short, as the Pay tab does, when more than one account keeps what's left).
- The page sends it (`setNotificationSchedule`) 2 s after any change and on every start. Time 06:00–22:00.
- A daily WorkManager job (inexact; no exact alarms) runs from the chosen time, and each run books a one-off run for the next chosen time, as the daily job drifts: a run over an hour early books today's and posts nothing; otherwise it posts today's unposted entries and books tomorrow's. Switching on or changing the time after today's time posts today's at once.
- If Android only runs the check the next day, missed entries go out in a "late" wording ("Payday today", "Yesterday, …"); never from before notifications were on.
- One channel, "Reminders". Tapping opens Reminders. WorkManager reschedules after a restart.

## Bridge (`window.PaydayNative`)
- `saveBackup(json)`, `keepBackup(json)`, `listBackups()`, `readBackup(name)`.
- `share(json, fileName)` (backups only), `shareFiles(json)` (exports: one or two text files), `shareText(text, title)`, `shareUpdate(json, fileName, text, title)` (a backup file with the transfers as message), `sendFeedback(subject, body)` (to `FEEDBACK_EMAIL` in `MainActivity.kt` and `export.js`). Text at most 20,000 characters.
- `pickBackupFile()`, `lockAvailable()`, `lockEnabled()`, `setLockEnabled(on)`, `setTheme(theme)`, `haptic(kind)`, `setNotificationsEnabled(on)`, `notificationsEnabled()`, `notificationsAllowed()`, `setNotificationSchedule(json)`.
- Results come back through `window.paydayNativeEvent(type, value, ok)`: `"lock"`, `"notify"`, `"import"` (a backup's text, or a reason) and `"open"` (`"due"`, from a notification).
- Absent in a browser, where the page works without it. Only the bundled page can load.

## Permissions
- `USE_BIOMETRIC`: the optional app lock (no prompt).
- `POST_NOTIFICATIONS`: asked only when notifications are switched on.
- `RECEIVE_BOOT_COMPLETED` and `WAKE_LOCK`: added by WorkManager so the daily check survives a restart. Its `ACCESS_NETWORK_STATE` and `FOREGROUND_SERVICE` are removed in the manifest.
- `uk.whiteboard.payday.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`: added by AndroidX Core, app-private.
- No INTERNET, network state, storage, camera, contacts or exact alarms. Files use content links and the system picker. `build.sh` fails if INTERNET ever appears.
